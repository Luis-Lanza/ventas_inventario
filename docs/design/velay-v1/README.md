## Compact gallery trial

The compact-gallery trial supersedes the fixed three-/four-column counts below for Sales, Inventory and Catalog. All three use adaptive tracks targeting a minimum width of 14rem (or the available width on narrower windows), 5rem-high contained images, and reduced card padding/gaps. Text and 44px control targets retain their existing scale. Short final rows keep the same card width. Sales detail/add actions share a row; table presentation is unchanged.

The acceptance target is two complete product rows in a window like the reported 1896 × 1030 screenshot. This is not a guarantee for every window, zoom level or long product description: preserve readable content and scrolling instead of clipping cards. Browser/native visual acceptance remains required; CSS cascade tests alone do not prove visible row counts.

Use available window height rather than indefinitely growing panels. In short windows, allow the modal body to scroll without making payment controls or footer actions unreachable. Use native scrolling, avoid redundant nested scrollbars, keep keyboard focus visible, and prevent background scrolling while the modal is open. Existing pagination is not replaced by infinite scrolling.

No additional scroll mockups are required. Validate these rules in the running app with enough products to overflow each region, different window sizes, keyboard navigation and focus changes.

The sale-success modal appears only after a real successful confirmation; do not stack it on top of the checkout dialog. Only “Nueva venta” dismisses the receipt and starts a clean draft; Escape and outside-click never dismiss it. Closing must never undo the persisted sale or expose its old cart for another charge. Focus transfer and the transition to a fresh sale require functional checks before implementation is considered complete.

For Inventory operation modals, closing discards the draft immediately without a discard-confirmation step; “Nueva operación” returns to the existing listing. Pending saves block dismissal and duplicate submission. A successful persisted response closes the modal back to the same listing view, query, filters and page, and uses the existing top-right action notification; a provider-free screen retains equivalent success/advisory feedback. Failures preserve input and error feedback, including retry identity and existing password-clearing rules. Keep stock-entry validation and physical-count password authorization intact. Button-to-modal expansion, contraction and entry/count transitions are presentation only: they must not delay persistence, replay actions or retain credentials after discard. Preserve focus restoration, bounded body scrolling, cleanup and reduced-motion fallbacks; native Windows visual acceptance remains a separate check.

For a Catalog product with many attributes, keep modal height bounded to the available window and allow a single native body scroll, without a second nested attribute scrollbar. Use a readable two-column attribute layout at the intended desktop size and adapt smaller windows without shrinking labels or controls. Verify many attributes, long labels, keyboard navigation and focus/scroll to invalid fields in the running app; no additional static overflow mockup is required. The overlay must cover the entire visible background, including lower result rows and pagination.

Future GSAP motion should connect actions and screen transitions, including the requested button-to-modal effect. Static screenshots do not demonstrate executable motion. Transactions must never depend on animation completion; preserve pending states, focus, accessibility, cleanup and reduced-motion behavior.

## Backup/restore implementation notes

The local operations now use equal rounded cards, an inset last-backup fact list and a public-only candidate summary. Restoration reuses `ConfirmationDialog` through a restore-only presentation seam and the existing checkout frame-motion driver. Cancellation clears acknowledgement immediately; contraction never gates cancellation or persistence. Mounted tests cover presentation, acknowledgement reset, focus return, pending guards and motion completion/resize/unmount; the shared driver tests cover reduced motion and invalid geometry. Native Windows visual acceptance, including short-window scrolling, remains outstanding.

## Product onboarding implementation notes
